## Required scenario coverage

| Scenario group | Required observation |
|---|---|
| Common execution | CLI versus foreground MCP and CLI versus asynchronous MCP contend across distinct project roots on one Installation and capacity-one lock. Each admitted review acquires once; its roles run in parallel. |
| Waiting and identity | Persisted key/payload replay, queue observation timeout, reconnect with the original invocation/run, abandoned-request cancellation through native request ID and grant/cancel race preserve one review dispatch. |
| Borrowing | Matching reference passes read-only validation; wrong Installation/lock, unknown grant, stale generation, expired deadlines and ended state refuse. Neither success nor child cancellation renews/cancels/releases a parent or silently reacquires. |
| Loss and recovery | Renewal failure, maximum-hold expiry, caller loss and controller restart stop new dispatch, request native cancellation/drain and preserve actual outcomes, including unknown drain and possible overlap. |
| Partial role failure | Retain original accepted reports, terminate native work and release before asking the user. Allow an unrelated waiter to proceed without publishing mixed-run coverage or rerunning roles. A newly authorized full review gets new FIFO position. |
| Provider-free compatibility | Local preflight, receipt-bound reads and no-change targets keep zero provider calls and require no grant. Existing source selectors, binding, requirements assessment, publication and error precedence remain valid. |
| Migration and skill | Real prior configuration/history/retry/active obligations survive supported migration; actual CLI, both MCP modes, full matching skill files and fresh-session discovery work on the released combination. |
| Automatic/manual guest | Record actual operator observations and staged case evidence. Automatic recipe cleanup/inventory finishes before exit; manual cleanup/inventory finishes while awaiting_manual before manual complete triggers collection. Collect/export afterward. |

Guest fault/contention scenarios use synthetic repositories, an isolated guest
controller/resource and stub providers. Shared `utm-macos` occupancy is acquired
once at the approved outer Haepari boundary; nested guest work never reacquires
its occupied parent VM. Isolated test locks cannot justify concurrent live
calls on shared production accounts. Stub/Haepari fixtures alone and VM-only
results cannot establish the released Mulgae obligation.

## Effect and release boundaries

Implementation approval does not authorize commit, push/tag/publication,
installation, host authentication/configuration/provider/profile changes, live
provider campaigns, broker operations or VM power actions. Resolve each needed
grant before its dependent effects. Preserve host Sorage as the real coordination
channel, all shared host account state and foreign hooks. Haepari never supplies
review execution authority. Preserve uncertain effects; do not retry a review
because its lock request can be replayed.

Use established repository gates and exact-candidate release policy. This
runtime change is ineligible for the patch-only version-increment waiver.
Missing release/provider/install authority leaves the affected release or final
Task incomplete; do not downgrade due criteria to skips. Aquarium alone accepts
its consumer return and updates its supported Mulgae floor. Shared legacy
infrastructure removal belongs to Aquarium EPIC-033/TASK-101.
